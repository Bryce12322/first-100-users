# 状态、效果与定时跟进

## 最小持久状态

优先复用用户已有运营记录。需要新建时使用明确的用户工作目录，或建议独立于公共 Skill 的产品目录，例如 `${CODEX_HOME:-$HOME/.codex}/first-100-users/<product-slug>/`。遵循文件权限，不静默把运营记录写入源码仓库。

两个文件即可，不要求数据库或专有服务：

- `campaign.md`：事实和来源、未知项、人群、实验、指标、授权、已配置跟进任务。
- `activity.jsonl`：动作和后续事件的追加台账。

slug 基于用户确认的产品身份，档案保留官网/商店标识，避免重命名后重复活动。私有资料、真实账号和发布记录不打包进公共 Skill。

不存密码、cookie、token、API key、完整客户名单和无关私信。只保存跟进与防重复必要信息。不能持久化就交付恢复摘要，说明下次不能自动恢复。

## campaign.md 内容

```text
产品：身份、官网、体验入口、目标地区与语言
事实：能力、限制、价格、权限、首次核心操作；逐项注明证据类型/来源/日期
阶段与未知：已有证据、缺失数据、当前瓶颈
人群与场景：本轮聚焦、排除项、现有替代方案
实验：experiment_id、人群、方法、表达、一个验证问题、成本、观察窗口、停止条件
指标：有效使用事件、周期、数据来源、归因边界
授权：账号/渠道/对象、动作范围、费用、有效期、用户授权出处
跟进：任务 ID、状态、时区、频率、结束条件、读写范围、最近检查时间
```

## 活动事件

未知字段用 `null` 或空列表，不估算补齐。以下仅为格式示例，不代表实际已发送：

```json
{"event_id":"event-001","action_id":"action-001","experiment_id":"experiment-001","recorded_at":"2026-10-19T10:00:00+08:00","event_type":"prepared","channel":"forum","account":null,"target_url":null,"dedupe_key":"product|forum|thread|reply","authorization_ref":"campaign.md:授权","content_summary":"针对具体问题准备的回复","content_path":null,"artifact_url":null,"evidence":[],"observed_at":null,"visibility":null,"outcome":null,"next_check_at":null,"stop_reason":null}
```

按实际填值。`content_path` 可指向已批准内容的本地副本；确有恢复需要且无敏感信息时才保留全文。`dedupe_key` 至少区分产品、平台、原始对象和动作类型；去掉无关追踪参数，但不丢评论 ID，不误合并不同对象。

新状态追加事件，不覆盖历史，后来移除也记录。按 `action_id` 的最新事件与历史决定下一步；未决提交、待审、拒绝和删除阻止重复联系。登记与核实减少重复，但不声称跨设备并发的强去重保证。

## 指标与归因

和用户明确有效使用：优先定义一个核心价值事件，例如第一次保存项目、生成可用结果或完成真实任务，不把登录、安装自动等同获得价值。

分别记录触达、兴趣、获取、激活、持续价值、商业结果：

- 触达：真实可观察曝光，读不到则未知。
- 兴趣：相关回复、明确愿意体验。
- 获取：有证据的访问、安装或注册。
- 激活：完成约定核心操作。
- 持续价值：适合产品周期内再次使用。
- 商业结果：真实付费或约定目标。

不要求完整漏斗，只在分母和口径可比时算比例。人工试用、好友、同行与自然流量分开，不把反馈样本当客户样本。

可用已获批准的分析工具、后台聚合数据、试用反馈、来源报告。UTM 只帮助识别部分访问，不保证跨商店安装归因。不擅自加追踪、上传个人数据或创建含身份的链接。

| 观察信号 | 下一步 |
|---|---|
| 无匹配对象 | 改检索或方法，不硬发 |
| 不理解产品 | 调整场景表达，确认功能边界 |
| 有兴趣却没体验 | 检查入口和门槛，可提议协助 |
| 体验但没完成核心操作 | 跟进首次使用，暂缓扩大曝光 |
| 完成后不再使用 | 判断低频需求或价值不足 |
| 持续使用与合格推荐 | 评估可重复方法，逐步扩展 |

小样本用于学习，不宣称显著性或因果关系。观察窗口未结束不急于判失败。

## 执行结束后的询问

本轮有值得跟进的内容、用户未拒绝且无等价任务时，问一次：

> 是否需要我设计一个定时任务，检查这批内容的新回复和审核状态，整理需要处理的问题？默认只检查和准备建议，不自动发布或回复。

只同意设计则给方案。明确要求创建且范围足够后才调用调度工具；复用匹配任务，不重复创建。用户拒绝或要求不要提醒时尊重选择。

## 定时任务约定

创建前明确：

- 目标：跟进已有实验还是找新机会；两者分别授权。
- 对象：真实产品档案、已发布链接和获准数据来源。
- 时间：用户时区、频率、窗口、试行期限或结束条件；不猜主机时区。
- 权限：能读、能准备什么；如允许发送，账号、对象、内容范围和持续授权期限是什么。
- 上限：每次时间、现金、处理数量，不擅用新付费服务。
- 通知：什么变化值得通知，无变化如何处理，使用调度器真实支持的设置。
- 停止：拒绝、移除、警告、许可到期、预算上限或用户取消。

默认建议有限周期，由用户决定；默认只读检查和草稿，不因日程触发而必须发布。自动外发仍需平台许可、持续授权和合规接口，不能继承一次性发送许可。

## 任务提示词结构

实际创建时用自然语言填写真实路径、对象和边界，不保留未填写字段：

```text
读取指定产品档案和台账，仅检查获准实验链接和数据来源。
对比上次检查，识别新增回复、审核/移除状态和已证实体验反馈。
核对账号和访问权限；登录失效或来源不可读时记录阻碍，不扩大访问。
为需要处理的事项准备建议和草稿，不自动发送、不新增推广、不购买、不加追踪。
将证据、变化和下一步追加台账；无新变化不捏造进展。
在约定时间/费用边界内停止，遵守拒绝、移除和授权到期条件。
```

以调度器返回的 ID 和状态确认创建，记录到档案，告知暂停/取消方式。缺调度器、创建失败或无法读持久档案时说明未建立持续任务，不用当前回合睡眠或口头承诺冒充后台运行。
